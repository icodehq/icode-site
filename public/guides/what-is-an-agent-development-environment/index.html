What is an agent development environment?

An agent development environment (ADE) is a control surface for running CLI coding agents. It gives each task its own Git worktree, runs agents in parallel, tracks what each one is doing, and gives the human a place to review the result before it reaches main.

It is not a new model. It is not a chat window wrapped around a model. And it is not an IDE with an AI autocomplete bolted on. The defining shift is who the primary actor is: in an ADE, agents do the work, and the human supervises, queues, and reviews.

The category is still early. Most developers today use one agent in one terminal. An ADE becomes useful when that stops scaling: when you are waiting on agents, running independent tasks, or losing track of which session is doing what.

This guide is currently available in English only.

ADE vs IDE vs terminal

The three tools solve different problems.

TerminalIDE with AIAgent development environment
Primary actor The developer The developer, assisted The agents, supervised
Isolation One working directory One project One worktree per task
Task model A process A file A durable task with states
Review You read the output Inline suggestions A diff and a review decision
Typical failure Context switching Suggestions that miss the codebase Unreviewed output, or agents colliding

A terminal is still the best place to run one agent on one task. An IDE is still the best place to write code yourself. An ADE is for the moment when you have more agent work than attention.

Some ADEs include an editor, a browser, or a chat surface. Those are useful features, but they are not the definition. The definition is the control loop: isolate the task, run the agent, observe the state, review the result.

The four components

A useful ADE has four components. Not every product has all four, and the weaker ones usually skip review.

1. Isolation

Every task needs its own working directory. Git worktrees are the standard mechanism: they share the repository's history but give each task a separate checkout, so two agents never edit the same file by accident.

A branch alone is not enough. Two agents can check out different branches in the same directory and still collide. The isolation has to be at the filesystem level. See Git worktrees for coding agents, explained.

2. A task model

An agent session is not a task. A task has a goal, a state, and a history. It can be queued, running, waiting for a person, completed, failed, or cancelled. A retry should be a new attempt, not an erased failure. A schedule should create ordinary tasks, not a separate system.

This is the difference between a terminal tab and a queue. The tab tells you a process exists. The queue tells you what work exists, what needs you, and what can wait. See durable tasks, not terminal tabs, and how to queue coding agent tasks.

3. Review

The agent finishing is not the same as the work being accepted. A review gate puts the diff in front of a person in the checkout where the agent worked, with the tests and the surrounding code. The review decision is separate from process exit, so a completed task can still be rejected.

This is the component most tools undersell. A green run proves the process exited; it does not prove the change is correct. See the review gate, and how to review AI-generated code.

4. A control plane

Once you run more than one agent, you need a view across projects: what is running, what is waiting, what failed, what is ready for review. Some ADEs add an assistant that reads the real queue and routes attention. The useful ones are bounded: they can tell you what needs you, but they cannot approve, merge, or push on their own.

When you need one

You probably need an ADE when two or more of these are true:

  • You regularly run more than one coding agent.
  • You spend time waiting for an agent, then context-switch to another task.
  • You have independent tasks that could run at the same time.
  • You review agent output before merging, or you wish you did.
  • You lose track of which session is doing what.
  • You want the work to stay on your machine.

The trigger is not ambition. It is the moment your attention becomes the bottleneck.

When you don't

You probably do not need an ADE when:

  • You run one agent on one task at a time.
  • You do not review agent output, and the work is low-stakes.
  • You want a chat-first assistant rather than a CLI agent.
  • You need remote servers, a mobile companion, or Slack/Linear bots more than you need a local review gate.

That last point matters. Some ADEs are broader than others. Orca, for example, supports remote servers, mobile companions, and bots in Slack, Linear, and GitHub. If those are requirements, a broad ADE is the better fit. If your bottleneck is review and local control, a narrower ADE can be the better fit.

Common misconceptions

“An ADE is a new model.”

No. It is a control surface for the CLI agents you already use. You keep your subscriptions and your agent choice; the ADE changes where and how the work runs.

“An ADE is a chat UI.”

A chat surface can be part of an ADE, but it is not the definition. A chat window with a model behind it still has one conversation, one context, and no filesystem isolation. The defining features are worktrees, task state, and review.

“An ADE is a terminal multiplexer.”

tmux and split panes show you processes. An ADE tracks tasks: what is queued, what is running, what is waiting for a person, what failed, and what is ready to review. A pane can show a process; it cannot tell you what needs your judgment.

“An ADE is only for large teams.”

The trigger is not team size. It is the number of independent tasks you are running and how much attention they consume. A solo developer running three agents on three features can benefit more than a large team running one agent at a time.

“An ADE replaces the IDE.”

It does not have to. Many developers keep their editor for hand-written code and use the ADE for agent work. The two can coexist; the question is where the agent runs and where the review happens.

Examples

The category is still forming, so the products differ.

  • Orca is a broad agent IDE: desktop, mobile, remote servers, an embedded browser, and bots. It is MIT-licensed and supports many CLI agents.
  • iCode Workbench is a review-first, local-first ADE: a durable queue, a review gate, worktree isolation, and a bounded assistant. It is AGPL-3.0 and pre-1.0. This is our product, so treat the comparison accordingly.
  • Conductor is a polished, Mac-only workflow with cloud workspaces.
  • Paradev (formerly Superset) is a team agent workspace with worktree-per-task.
  • Emdash focuses on cloud coding agents for teams, with issue-tracker intake.
  • Paseo focuses on running agents remotely from a desktop app or CLI.

Verify current details and licensing on each project's site. The category changes quickly.

How to evaluate one

A short checklist:

  1. Isolation: does each task get its own worktree, or only a branch?
  2. Task model: are there explicit states, retries, and schedules?
  3. Review: can you review the diff in the checkout, and is the review decision separate from process exit?
  4. Data: does the state live locally, and is there telemetry?
  5. Agents: does it support the CLI agents and subscriptions you already use?
  6. License and platform: does the license fit your organization, and does it run on your OS?

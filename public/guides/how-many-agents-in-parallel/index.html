How many coding agents should you run in parallel?

The honest answer is not a number. It is the largest fleet you can still review well. Past that point, more agents produce more diffs, not more accepted work.

This guide gives you a way to choose the number instead of guessing: start with two, measure the review loop, and add a slot only when the queue and the review are both keeping up.

This guide is currently available in English only.

The bottleneck isn't the model

Agents can produce diffs faster than a person can review them. If you measure only agent throughput, the fleet looks great; if you measure accepted, reviewed work, the queue is the constraint.

This is why “run ten agents” is not a strategy. Ten agents may produce ten diffs in an hour, and one person may review two of them well. The other eight become a backlog, and a backlog of unreviewed diffs is not progress.

Task independence

Parallelism only pays off for independent tasks. Two tasks are independent when they touch disjoint files, have no shared contract that must land first, and can be verified separately.

If task B needs the result of task A, run them in sequence. If both need a new type, a route entry, or a schema change, land that contract on main first; otherwise the two branches will invent different versions of it. A fleet does not make dependent work faster; it makes the dependency harder to see.

Review capacity

Review capacity is the real limit. Measure it directly:

  1. How long does a typical review take? Not a skim; a real read of the diff, the tests, and the surrounding code.
  2. How many can you do in a focused hour? For most people, one to three, depending on the diff size.
  3. How many hours per day do you actually have for review? Not the whole day; the time between other work.

The product of those numbers is your rough ceiling. If a review takes 30 minutes and you have two focused hours, four reviews is a full day. A fleet that produces eight diffs a day is already over capacity.

The limit is not fixed. Smaller tasks and a faster test suite raise it; large diffs and a flaky suite lower it. The point is to choose the fleet size from the review loop, not from the machine. Measure your own review speed before you choose a fleet size: the number that matters is how many diffs you can read, not how many agents you can start.

When review is the bottleneck

Do not add an agent to fix a review bottleneck. Fix the review loop:

  • Make the tasks smaller. A 200-line diff is faster to review than a 600-line diff, and it is less likely to hide a semantic conflict.
  • Make the tests faster and more trustworthy. A five-minute suite lets you run the combined result after every merge.
  • Review the risky files first. Auth, data, shared interfaces, and dependencies before formatting and docs.
  • Reject oversized diffs. “Too large to review” is a process finding; split the task and re-run.
  • Add a reviewer before you add a slot. A second reader raises capacity more than a fourth agent.

Machine and cost limits

The machine sets a second ceiling: CPU and memory for the agents, the dev servers, and the test suites; ports and databases for each worktree; and the rate limits of the model or agent provider. Cost is the third: tokens and subscription usage scale with the number of concurrent sessions.

These are easier to see than review capacity, which is why people optimize for them and miss the real bottleneck. A machine that can run ten agents is not a reason to run ten.

A concrete example: four agents each running a ten-minute test suite can saturate four cores and make every review wait for a test run. The fleet's wall-clock time improves, but the reviewer's does not. If the machine is the limit, reduce concurrency or move the suite to a faster runner; adding agents will only queue more work behind the same CPU.

A simple starting formula

  1. Start with two. Two independent tasks, two worktrees, one reviewer.
  2. Run for a week. Track queue wait time, review time, merge failures, and rework.
  3. Add one slot only when the queue is consistently empty and every diff is still being read.
  4. Remove one slot when the review backlog grows for more than a few days or the rework rate rises.
  5. Do not add a slot to fix a slow agent. Fix the task scope or the harness first.

The number will be different for a solo developer, a two-person team, and a team with a dedicated reviewer. That is expected. The formula is the same; the inputs are not.

A worked example: two vs four

Week one: two agents, eight independent tasks, one reviewer. The queue is empty by day three, every diff is read, and two merges need a small rebase. Review capacity looks like roughly four tasks a day.

Week two: four agents, sixteen tasks. By day two the review backlog is six, two diffs are merged after a skim, and one semantic conflict reaches main. The agents were faster; the accepted work was not.

The useful conclusion is not “four is bad.” It is that the fourth slot exceeded review capacity for that week's task sizes. The next attempt should use three slots, or keep four and make the tasks smaller and the test suite faster. Add a slot when the queue is empty and review is current; remove one when the backlog grows.

These are starting points, not rules. The number that matters is the one your review loop can sustain.

Signals to add or remove agents

  • Add: the queue is empty, review is current, merges are clean, and you have independent tasks waiting.
  • Remove: the review backlog is growing, the same files conflict repeatedly, or the rework rate is rising.
  • Hold: the queue is empty but review is behind. The constraint is review, not agent count.
  • Fix first: flaky tests, missing env setup, port conflicts, or a task that is too broad.

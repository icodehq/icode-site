From one agent to a fleet: when you need a workbench

One coding agent in one terminal is a good setup. It is simple, it is easy to review, and it does not need a queue. The question is not whether a fleet is more powerful. It is whether your work has outgrown the single-agent loop.

This guide is about the moment you add a second agent — and the few things you should put in place before you add a third.

This guide is currently available in English only.

One agent is fine — until it isn't

A single agent is not a beginner setup. For one task at a time, it is often the best setup: one context, one checkout, one diff to review. Adding a fleet too early creates coordination work you did not need.

The single-agent loop starts to strain when the work becomes independent but the tooling stays serial. You give an agent a task, wait, and then give it the next task. The agent is busy; you are waiting. Or you open a second terminal, then a third, and start tracking sessions in your head. The work did not become complex. The coordination did.

The trigger is not ambition or team size. It is the ratio of independent work to your attention. When that ratio crosses a threshold, a workbench stops being overhead and starts being the thing that keeps the work legible.

Three signals you need a fleet

  1. You wait on the agent while independent work is ready. If you have a second task that does not depend on the first, the waiting time is pure loss. Two tasks can run at once without becoming a fleet.
  2. You are tracking sessions in your head. When you have to remember which terminal is on which branch, which one is blocked, and which one finished, the sessions have outgrown the interface. A queue is cheaper than memory.
  3. Review is the bottleneck — or it is being skipped. If you review every diff and the queue of unreviewed work is growing, you need a review gate, not more agents. If you are skipping review because you cannot keep up, that is the signal that the workflow needs a workbench.

Two of these three is usually enough. One alone might be a bad week.

The first two-agent setup

Start with two tasks, not five. Pick work that is genuinely independent: different files, different tests, no shared schema change. Then set up the smallest loop that keeps them from colliding.

  1. Create one worktree and one branch per task. Name them after the task. Do not run two agents in the same checkout. Here is how worktrees work.
  2. Give each task a scope. Owned paths, a done-when command, and an out-of-scope list. If the two tasks share a file, they are one task until the shared change lands.
  3. Run both agents, but review one at a time. Two agents can run in parallel; your review cannot. Read the first diff, decide, then read the second.
  4. Merge serially. Rebase the second branch on main after the first merge, run the tests, then merge. Do not merge both and test afterward.
  5. Write down what broke. A shared file, a port, an env var, a merge conflict. That list is the setup for the next attempt.

If this feels like too much process for two tasks, keep one agent. The process is the point: it is what makes the third and fourth task safe.

What breaks first

The first failures are predictable. They are rarely model failures.

  • File collisions. Two agents in one checkout overwrite each other. A worktree per task fixes this before it happens.
  • Shared-state surprises. A fresh worktree has no .env, no node_modules, and no local database. Two dev servers both want port 3000. Set up each checkout deliberately.
  • Merge order. Two branches can pass alone and fail together. Merge one at a time and test the combined result.
  • Review load. Two agents can produce two diffs faster than one person can read them. The limit is review capacity, not agent count.
  • Lost sessions. A terminal dies, the app restarts, and the work disappears with the process. If the task matters, the session should outlive the window.

A concrete example: one agent adds /auth/refresh and the other adds /billing/portal. Both edit src/routes.ts. Each branch passes its own tests, so both look green. The second merge silently drops the first route, and the combined test suite only catches it if it exercises both paths. The fix is not a better model; it is landing the shared route-table edit before the parallel work, or giving the route table to one task.

None of these requires a platform to understand. They require a deliberate setup. A workbench is one way to make that setup the default.

The minimum viable workbench

You do not need every feature of a mature ADE to run two agents. You need three things:

  1. Isolation. One worktree per task, so the agents cannot overwrite each other.
  2. A task list with states. Even a simple list is enough at first: queued, running, waiting for me, done. The states tell you what needs attention without opening every terminal. See how to queue coding agent tasks.
  3. A review gate. A diff in the checkout where the agent worked, and a decision that is separate from the process exiting.

Everything else — schedules, retries, a cross-project assistant, mobile, remote servers — is an optimization. Useful, but not the minimum.

iCode Workbench packages those three things: worktrees, a durable queue with explicit states, and review in the session checkout. It also adds a bounded assistant and 44 CLI agents, but the three are the reason it exists.

When not to add a second agent

A fleet is not a maturity badge. There are good reasons to stay with one agent:

  • The work is sequential. If task B needs the result of task A, running them together creates a merge problem, not speed.
  • The tasks share files. Two agents editing the same route table, manifest, or migration directory are one task until the shared change lands.
  • The test suite is flaky. A green run is only useful if you trust it. Fix the suite before you multiply the number of green runs.
  • You cannot review two diffs a day. The bottleneck is your attention, not the agent count. Adding agents makes the queue longer, not the work faster.
  • You are avoiding a design decision. Parallel agents do not resolve an ambiguous interface. They produce two implementations of it.

A single agent with a clear scope and a review gate is often better than two agents with neither. Add the second agent when the work is independent and the review loop is already working.

Next step

If the signals above sound familiar, do not start by adding five agents. Read the parallel coding agents guide and run two independent tasks for a week. If review keeps up and the merges are clean, add a third. If review does not keep up, fix the review loop before adding anything.

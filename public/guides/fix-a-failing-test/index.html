iCode Agent · Guide · Workflow

Fix a failing test.

The core loop of a coding agent: reproduce the failure, understand it, change the code, and prove the change. iCode Agent runs that loop against your real repository.

The task

Start iCode Agent in the project and describe the goal:

Fix the failing tests in this repository.

Naming a specific test narrows the work, but iCode Agent can find the failure itself by running your test command.

What happens

  1. Explore. It reads the relevant files and searches the tree to locate the failing code.
  2. Reproduce. It runs your test command and reads the actual failure.
  3. Repair. It makes a targeted edit — not a rewrite — and shows the diff.
  4. Verify. It runs the tests again and reports the result. If they still fail, it keeps going.

Every step is visible: each tool call and a live preview of its output stream past as the agent works.

Steering it

If the agent heads the wrong way, you do not wait for it to finish:

  • Type a message and press Enter to redirect it mid-task.
  • Press Esc to abort, or Alt+Enter to queue a follow-up.
  • Press Ctrl+O to expand a tool result you want to read in full.

Good prompts for this workflow

Fix the failing tests and explain what the bug was.
The test in tests/auth.test.ts is failing — find out why before changing anything.
Make the failing test pass without changing the test itself.

Before you start

Start from a clean worktree, know the exact test command, and note whether the failure is deterministic. If the test is flaky, run it twice before asking the agent to fix anything. A fix for a flaky test is a guess until you know the failure is stable.

When the fix is wrong

Watch for three shortcuts: changing the test to match the code, weakening an assertion, or fixing the symptom without the cause. If the diff touches both the test and the production code, ask which change is the fix and which is the accommodation. A passing suite is not proof if the test was changed to pass.

If the agent cannot explain the root cause in one or two sentences, stop and ask for the evidence: the failing output, the line that caused it, and why the change addresses that line. A plausible story is not a diagnosis.

A worked example

Take a failure in tests/report/builder.test.ts. The agent should run that file first, read builder.ts and the test, and identify the branch that produces the wrong output. A good fix changes the production branch, not the expected value in the test. After the edit, it runs the file, then the full suite, and reports both results. Then ask it to explain why the branch was wrong and what input triggers it.

If it changed the expected value, stop: the test was the specification, and the fix just rewrote the specification. If it changed a shared formatter used by other tests, run those tests too; the fix may be correct for this case and wrong for another. A second run is not paranoia. Run the failing file, then the suite, then the file again. If the result changes, test isolation is part of the problem.

The point of the example is the order: reproduce, read, change the smallest production branch, verify at two levels. The agent can do all four; your job is to check that it did not skip the first or the last.

What to verify

Before you accept the change: the test failed before the fix, the same test passes after, the assertion was not weakened, the diff is limited to the failing path, and no unrelated files changed. Run the command yourself. If the suite is slow, run the failing file first, then the full suite before you commit.

A failure mode: the flaky test

Sometimes the failure is environmental: order dependence, a shared fixture, a timing assumption. Ask the agent to reproduce it twice and report whether the failure is stable. If it is not, fix the test isolation before the code. Otherwise the fix will pass once and fail again in CI.

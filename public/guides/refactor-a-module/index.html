Refactor a module.

Refactoring is mostly understanding: what calls this, what it calls, and what has to stay true while the shape changes. iCode Agent does that mapping against the real code before it edits anything.

The task

Name the module and the change you want, then let it map the blast radius first:

Refactor src/report/builder.ts. Extract the formatting into a
separate module, update all callers, and make sure the tests still pass.

Naming the file bounds the work. If you are unsure where the change belongs, describe the goal and let the agent find the boundary — but a named target keeps the change focused.

What happens

  1. Map it. grep and find locate the module's callers; read shows the code with line numbers so the agent can see structure, not guess at it.
  2. Plan the change. It identifies what moves, what stays, and every caller that must be updated.
  3. Edit in small steps. edit replaces one exact span at a time and shows the diff, so a review sees the change, not a rewritten file.
  4. Keep the tests green. It runs your suite — the safety net that makes a refactor safe rather than risky.

Nothing is rewritten wholesale: edit changes a target span and write is used only for genuinely new files. The diff is always visible before you accept it.

Reviewing the diff

This is where you earn the value: the agent proposes, you decide. A good prompt for a refactor asks for reasoning you can check, not just a result: 

Refactor the auth module. Show me the callers you found first,
then make the smallest change that removes the duplication.
Run the tests after each file you touch.

If a change is wrong, steer mid-task rather than reverting afterward — the agent has not committed anything, so a redirect is cheap.

Good prompts for this workflow

Find every caller of parseConfig() before changing its signature.
Extract the duplicated retry logic into one helper and update both call sites.
Explain what this module does, then suggest a refactor — but make no edits yet.

The last one is deliberately read-only: ask for the analysis, read it, and then ask for the change. For a large refactor that is often the better shape.

Before you start

Start from a clean worktree with a passing test suite. If the tests are already failing, fix or record those failures first; otherwise you cannot tell your refactor from the baseline. Write down the public surface that must not change: exported functions, types, routes, CLI flags. A refactor that changes behavior is a feature change wearing a refactor's clothes.

What "done" means

Done means the behavior is unchanged, every caller is updated, the tests pass, and the diff is mechanical enough to review. The change should be mostly moves, renames, and extraction — not new logic. If the diff adds a feature, stop and split it. The reviewer should be able to explain the change in one sentence without reading the whole file.

Failure modes

The most common failure is mixing a refactor with a feature. The agent sees a nearby improvement and takes it; the diff now changes behavior and shape at once. Ask for the refactor only, and put the feature in a separate task. The second failure is changing a public API without checking consumers. A refactor that updates the module but not its callers is not done.

The third is weakening tests to make the new shape pass. If the test changed, ask whether the behavior changed. The fourth is a broad rewrite: a diff that touches every file is hard to review and easy to get wrong. Prefer small steps with a green suite between them.

What to verify

Before you accept: the suite passed before and passes after; the public surface is unchanged or the change is intentional; every caller is updated; the diff contains moves and renames rather than new logic; no unrelated files changed; and the tests still assert the same behavior. Run the suite yourself, and read the diff in the order the change was made.

Migrate from Orca to iCode Workbench

Orca and Workbench can coexist. This is a five-step migration for teams that want a local, review-first task queue without giving up Orca's broader surfaces. You do not need to move everything at once; start with one task and decide after a week.

iCode Workbench is our product. This page is written to be useful even if you decide to stay with Orca; the “When to stay” section is not an afterthought.

This guide is currently available in English only.

What migration means

Migration is not a data import. Workbench does not import Orca tasks, sessions, bots, schedules, or settings. What transfers is your repository, your agents, and your subscriptions; the workflow is recreated task by task.

That is intentional. A queue that imports stale tasks and half-finished sessions creates a second source of truth. Start with one task that needs review, run it in both tools if you want, and compare the review experience. The unit of migration is a task, not a workspace.

Keep Orca installed during the evaluation. The two tools can coexist on the same machine, and Orca's worktrees are ordinary Git worktrees — they are not touched by Workbench.

Before you start

  • Install Workbench on Windows, Linux, or macOS. Keep Orca installed.
  • Open the same repository. Workbench creates a worktree per session; your existing Orca worktrees remain.
  • Know the review model. Review happens in the session checkout, and the review decision is separate from process exit.
  • Pick one task that needs review. A task with a real diff and a clear done-when command is a better test than a trivial one.

If you are new to the workflow, read how to run multiple coding agents in parallel and how to review AI-generated code.

Step 1: Install Workbench, keep Orca

Install Workbench and leave Orca in place. You are not committing to a switch; you are adding a review-first queue beside the tool you already use. Both can run at the same time.

Workbench is free and open source under AGPL-3.0. It is pre-1.0, so features and storage schemas may change between releases. If AGPL-3.0 is a blocker for your organization, Orca's MIT license may be the decisive difference; that is covered below.

Step 2: Open the same repository

Add the repository to Workbench. New sessions get their own Git worktree and branch, starting from the current HEAD. Your existing Orca worktrees are untouched; they are just directories with branches.

If you want to reuse an Orca worktree's branch, create a new session from that branch in Workbench. Do not point two tools at the same working directory at the same time; the isolation is per checkout, and sharing one defeats it.

Step 3: Move one task, not the queue

Pick one task that needs review and queue it in Workbench. Set the slot limit to 1 for the first run: one task, one checkout, one review.

Give the task a goal, owned paths, a done-when command, and an out-of-scope list. The task statement is the part that makes the review possible; without it, you are comparing two tools on a vague diff.

For the queue model, read how to queue coding agent tasks.

Step 4: Review in the session checkout

When the agent finishes, review the diff in the checkout where it worked. Use Files, Search, and Source Control; leave line notes; run the done-when command yourself. Then make the review decision: accept, revise, or reject.

The decision is separate from process exit. A completed task can still be rejected, and a rejected task can be revised and re-reviewed. This is the part of the workflow to compare with Orca: not which tool has more features, but whether the review is a real gate or a summary.

Step 5: Decide after a week

Run one or two tasks a day for a week. At the end, ask:

  • Did the review happen in the checkout, or did you fall back to reading a summary?
  • Did the queue tell you what needed you, or did you track sessions in your head?
  • Did the work stay on your machine?
  • Did you miss Orca's mobile, remote, browser, or bots?

If the answers favor Workbench for the review-gated work, keep it for that work. If you need Orca's broader surfaces, keep Orca for those and use Workbench for the tasks that need a review gate. A split setup is a valid outcome.

Compare the workflow you actually run, not the feature list. A tool with fewer surfaces can still be the better fit if the review is the part you need to fix.

A week-one plan

  1. Days 1–2: install, open the repository, run one review-needing task, and review the diff in the checkout.
  2. Days 3–5: run one or two tasks a day. Note review time, queue wait time, and any merge or setup problem.
  3. Days 6–7: compare the notes with your Orca week. Decide whether Workbench owns the review-gated work, whether Orca keeps the broader surfaces, or whether you stay with Orca.

A split setup is a valid result. The goal is not a winner-takes-all migration; it is a review loop that actually happens.

What doesn't transfer

  • Tasks and history. Recreate the task in Workbench; there is no import.
  • Orca sessions and bots. They stay in Orca. Workbench has no Slack, Linear, or GitHub bot integration.
  • Schedules. Recreate the ones you still need as ordinary queued tasks.
  • Orca settings and presets. Set up Workbench's defaults separately.
  • Git history and worktrees. These are in the repository, not in either app; they remain.

When to stay with Orca

If any of these is a requirement, Orca is the better fit today:

  • Mobile. Orca has iOS and Android companions; Workbench is desktop-only.
  • Remote and SSH. Orca supports remote servers, SSH worktrees, and experimental cloud VMs; Workbench is local.
  • Browser and Design Mode. Orca embeds Chromium and can send a clicked element to an agent; Workbench does not list that surface.
  • Slack, Linear, and GitHub bots. Orca takes work from those surfaces; Workbench does not.
  • Maturity. Orca is on a 1.4.x release line; Workbench is pre-1.0.
  • License. Orca is MIT; Workbench is AGPL-3.0. If your organization cannot accept AGPL-3.0, that is decisive.

A migration page that hides this is a sales sheet. If you need those surfaces, keep Orca and use Workbench only for review-gated work — or stay with Orca entirely.

Migration checklist

  1. Install Workbench; keep Orca installed.
  2. Open the same repository; confirm existing Orca worktrees are untouched.
  3. Pick one task that needs review; write the goal, owned paths, done-when, and out-of-scope.
  4. Set the slot limit to 1; queue the task.
  5. Review the diff in the session checkout; run the verification yourself.
  6. Record the review decision separately from process exit.
  7. Run one or two tasks a day for a week.
  8. Decide: Workbench for review-gated work, Orca for the broader surfaces, or both.

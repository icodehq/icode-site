GitHub Copilot in iCode Workbench

GitHub Copilot's CLI is a terminal coding agent from GitHub. In Workbench it runs as a primary harness: each session gets its own Git worktree, the task sits in a durable queue, and the diff is reviewed in the checkout where it was made.

This page is currently available in English only.

What GitHub Copilot is good at

  • GitHub-native work. Copilot's CLI fits teams already working in GitHub issues, pull requests, and repositories.
  • Your Copilot subscription. Use your existing GitHub Copilot account and model access; Workbench does not replace the agent or its provider.
  • Resumable sessions. Workbench can resume a Copilot session by id when the harness reports one.

Workbench changes where the session runs and how the result is tracked; it does not change Copilot's model behavior or permissions.

Why run it in Workbench

  • One worktree per session. Two agents in one checkout can overwrite each other; Workbench gives each its own branch and working directory.
  • A durable queue. A session is a process; a task has states. Workbench tracks queued, running, waiting, completed, and failed work.
  • A managed status hook. Workbench installs Copilot's status hook at ~/.copilot/hooks/icode.json, so the session row can report what the agent is doing. Without the hook, the session stays unknown rather than guessing.
  • Review in place. Files, Search, and Source Control live beside the terminal, scoped to the session checkout, with line notes and a separate review decision.

Setup

  1. Install the Copilot CLI using GitHub's official instructions, then confirm copilot --version works in your shell.
  2. Run it once outside Workbench so GitHub authentication and Copilot settings are in place.
  3. Install the status hook from Workbench's harness settings, and confirm the hook file exists at ~/.copilot/hooks/icode.json.
  4. Add the repository to Workbench and open it. The harness keeps its own credentials.

If Copilot is installed but Workbench does not see it, check that copilot is on the PATH of the shell Workbench launches. On Windows, a WSL target needs it installed inside the distro.

Launch and resume

Create a new session from New worktree, choose GitHub Copilot, and give the task a scope. Workbench launches copilot in the session checkout. Each session is independent: its own branch, its own terminal, its own context.

Workbench uses the resume recipe --resume=$TOKEN when a session id was captured. If the app restarts, the detached host keeps the PTY alive; sleep a session to stop the process and keep the checkout, then wake it to resume where the harness supports it.

Status at a glance

The session row shows the project, branch, target, and state. GitHub Copilot reports through the managed status hook; a session without the hook stays unknown rather than showing a false running. A concrete task

Task: “Add a retry to the pull-request review comment fetch.”

  1. Create a worktree from main and name the branch after the task.
  2. Scope the session: owned paths src/github/reviews/** and its tests; the GitHub client schema and route table are out of scope.
  3. Launch GitHub Copilot in the session checkout with the task statement and the done-when command.
  4. Queue the task if another session is running; one worktree per task.
  5. Review the diff in the checkout: run the GitHub client tests, check that the retry is bounded, and confirm the error path is covered.
  6. Decide accept, revise, or reject; merge after the combined result passes.

A GitHub integration can pass unit tests with a mocked client and still fail against the real API. The review should say which path was tested and which one needs a live check. The goal is a reviewed diff, not a faster terminal.

What the managed hook changes

The hook is what turns a terminal into a row with a state. Without it, Workbench can see the process but cannot distinguish running from waiting; the row stays unknown. The hook writes a small config file at ~/.copilot/hooks/icode.json and does not proxy model traffic or capture prompts. If you remove it, sessions still run; they just lose the status detail.

If you use Copilot's editor integration at the same time, keep the CLI session in its worktree; the two should not share a checkout.

Limits

  • Workbench does not embed GitHub Copilot's editor features. It runs the CLI agent in a worktree; GitHub's own IDE integrations stay in GitHub's tools.
  • Desktop only. Workbench is a desktop app; there is no mobile or remote server. If you need those, Orca is the broader tool.
  • Pre-1.0. Workbench is still changing; verify current behavior before standardizing a team on it.

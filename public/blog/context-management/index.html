The context window is a budget.

A coding agent is mostly a loop: explore, change, run, verify. The loop is cheap to describe and expensive to run, because every step lands in the context window and is paid for again on every request that follows.

Where the tokens go

An agent reading a file, searching the tree, running a test and reading a stack trace produces a lot of output — most of it useful exactly once. Left alone, that history grows until the request no longer fits the window. At that point an agent does one of two bad things: it truncates and loses the thread, or it stalls outright.

Neither is necessary. The output of a tool call is not equally valuable forever. A file you read twenty steps ago is usually summarizable; the result you got one step ago is what the current decision rests on. A context system should reflect that.

Three layers, each doing the cheapest thing

iCode Agent manages context at every boundary, from cheapest to most expensive:

  1. Cap at the source. Oversized tool output is capped as it is produced — spilled to a file with a short preview — so a single huge result cannot flood the window in the first place.
  2. Reduce at request time. Only when a request would exceed its input budget, older tool results are replaced by compact markers, oldest first, and only as many as it takes to fit. The current turn is protected: it is what the agent is working on.
  3. Summarize durably. When history truly overflows, older turns are summarized into one message with a recent tail preserved, so the session continues instead of ending.

Reduction must be reversible

Truncation loses information. The interesting design question is how to reduce without losing the thread. iCode Agent's answer is that a withheld result is not deleted — it is replaced by a structured pointer back:

  • A route to the full output. The marker names where the content still lives — the spilled file, or the file a read came from — so the agent can go back for detail instead of guessing.
  • Failure evidence is never withheld. Errors and failed commands are exactly the facts a long task depends on, so they survive even when everything around them is reduced.
  • Your history is never rewritten by reduction. Reduction is a request-time view only. The saved session keeps every result.

A worked example: one task, two strategies

Take a refactor that touches six files in a report module. The task is bounded, the tests are fast, and the reviewer will need to see the diff.

Strategy A is one long session. The agent reads the six files, runs the suite, follows a stack trace, edits, and reads the result. The context grows with every step. After enough turns the window compacts, and the summary keeps the goal but loses the exact line, the failed approach, and the reason the second attempt worked. The diff may still be correct. The reviewer cannot tell from the session what was ruled out.

Strategy B is a bounded task with a handoff. The agent works in its own worktree and, at a chosen point, writes a handoff note: the task, the constraints, the files and lines, what was tried and ruled out, the verification command, the review state, and the next step. A fresh session reads the note and continues. The code can be identical to Strategy A. The difference is that the second session starts with evidence, and the reviewer can check the same fields. The handoff costs a few minutes; the lost thread costs a review.

Why this matters for cost

Cost in a coding agent is not one number — it is the size of every request, multiplied by the number of steps. A smaller, well-managed context is not only cheaper; it is also what keeps a long task coherent, because the model is not drowning in stale output.

The goal is not the smallest possible context. It is the smallest context that still answers the question — with a way back to the rest.

What to measure

You cannot tell whether context management is working from the bad sessions alone. Log four numbers: window usage at the start of each turn, compactions per task, cache hit rate if the harness exposes it, and rework rate — changes that were reverted or re-explained after a compaction. A minimal log line is enough: 

{"task":"refactor-builder","turn":18,"window_pct":0.72,"compactions":1,"cache_hit":0.81,"rework":0}

The leading indicator is the combination: rising compactions with flat task completion means the task is too large, or the handoff is losing information. Fix the boundary before adding more context.

When to start fresh instead

Compaction is not the only move. Continue when the goal is unchanged and the context is still relevant. Rewind when a recent branch went wrong but earlier context is useful. Compact when the goal is unchanged but the context is noisy. Clear when you are switching to unrelated work. Start a new session or worktree when the task is new or independent. The test is simple: has the goal changed, or only the noise?

A new worktree is the cleanest boundary for independent work: the next session starts from a clean checkout and a bounded task, not from a summary of every branch and every unfinished experiment. For the queue model behind that, see durable tasks, not terminal tabs.

Three failure modes

Compacting too late. A summary written under pressure is worse than one written at a chosen boundary. If the window is already full, the model is summarizing a degraded conversation. Compact with a focus hint before the limit, while the task and the open questions are still clear.

Losing the constraints. Rules and invariants are exactly what a summary tends to compress. If a constraint must survive, restate it in the next prompt or keep it outside the summary. A task that remembers the goal but forgets the safety rule is not a safe task.

Reviewing the summary instead of the diff. The recap describes intent; the diff describes behavior. If the reviewer only reads the recap, the gate is a summary of a summary. Read the change in the checkout, run the verification, and decide from the evidence.

All three are handoff failures, not model failures. The fix is the same: make the boundary explicit, and leave evidence on both sides of it.

A long-task checklist

Before a long task, check six things: the task statement has a done condition and an out-of-scope list; each task has its own worktree and branch; shared contracts land on main before parallel work starts; the verification command is known and fast enough to run; a handoff note exists before context is compacted; and a reviewer is available for every completed task. If any item is missing, fix it before the first prompt — not after the first compaction.

A handoff template

A handoff note is not a transcript summary. It is a small structured artifact the next session — or the next person — can act on. Copy this into a plan file, task record, or commit message: 

## Task
<one sentence, copied exactly>

## Constraints
- <must stay true>

## Files and lines
- path/to/file.ts:62 — <why it matters>

## Tried and ruled out
- <approach> — <why it failed>

## Verification
- <command> — <last result>

## Review state
- <branch, commit, diff summary, open questions>

## Next step
<one action>

The fields earn their place: exact identifiers survive summarization, failed approaches prevent loops, verification lets the next session prove the fix, and review state tells a person what to inspect. For the decision that follows, see the review gate.

What good looks like

A good long-task session is not the one with the largest window. It is the one where the next person can reconstruct what happened without reading the whole transcript. The task statement names the goal and the constraints. The worktree holds only this task. The handoff note is written before the window is full. The verification command is in the note, and the diff is reviewed in the checkout where the agent worked.

That standard is deliberately boring. It does not depend on a model remembering a detail across forty turns. It depends on artifacts that survive the model: the task, the branch, the note, the command, the commit, the review decision. When the session ends, those artifacts are what remain.

The same standard applies to a fleet. If every task has the same artifacts, the queue is auditable: you can see what was asked, what changed, how it was verified, and who decided. The context window is a budget; the artifacts are the accounting. An auditable queue is not a bureaucracy; it is what lets a person trust a fleet without reading every transcript.

What a cross-project agent assistant should actually do

Another chat pane is not an assistant. A blank box that waits for you to paste the context, summarize the task, and explain what changed is a text field with a model behind it. The hard part of working with a fleet is not generating another answer. It is knowing what needs you across projects.

This essay is currently available in English only.

The chat-pane trap

Most “AI assistants” for coding start from the same shape: a chat box, a model, and a context window. You paste a stack trace, a diff, or a task description, and the model answers. It can be useful. It is also a blank slate every time.

The assistant does not know which tasks are running, which diffs are waiting for review, which session is blocked on a permission prompt, or what changed since yesterday. You are the integration layer. You copy state from the queue into the chat, and copy the answer back.

That is not an assistant. It is a second interface to the same work, with you as the API.

What Mira reads

Mira reads the real queue. Her answers come from projects, tasks, sessions, diffs, and review state — the same state you see in the sidebar, not a pasted summary of it.

That changes the questions you can ask:

  • What needs me right now?
  • What is blocked, and on what?
  • What changed since yesterday?
  • Which tasks are ready for review?
  • Draft a review note for the auth task.

The answer to “what needs me?” is not a generic list of best practices. It is the actual review-ready work, the failed task, the waiting permission prompt, and the uncommitted change in the project you forgot was open.

One conversation spans every repository. That matters because the work does: a blocked task in one project can depend on a contract change in another, and a review queue does not stop at a repository boundary.

A Tuesday morning

You open the workbench. Three tasks completed overnight. One is waiting on a permission prompt. One failed on a missing credential. The review queue has two diffs.

Mira's first message is not a summary of the repository. It is: “Two review-ready: auth and billing. The docs task failed on a missing token. The migration is waiting for your approval.” You handle the approval, then read the auth diff. The assistant did not do the work; it told you where to look.

The billing task is in one repository. The permission change it depends on is in another. A per-project assistant would miss the dependency. A cross-project assistant can point at it without opening every tab.

What she can do

Mira is not read-only. Through validated actions, she can:

  • create, cancel, retry, and archive tasks;
  • message task sessions and project supervisors;
  • record non-binding review recommendations.

Those actions are typed and bounded. She is not inventing shell commands or editing files through a side door. She is operating the same queue and session model you are.

That is the useful middle ground: enough agency to move work along, not enough to become another uncontrolled agent.

What she cannot do

Mira has no shell and no project working directory. She cannot approve a proposal, decide a review, merge, push, or edit project code.

The list is short, and it is the point.

An assistant that can merge is another agent with a larger blast radius. You would have to audit its reads, its writes, and its judgment. The value of a bounded assistant is that you do not have to treat every answer as a potential commit.

She can tell you what needs a decision. She cannot make the decision. She can draft a review note. She cannot approve the diff. She can retry a failed task. She cannot rewrite the code herself.

The judgment stays with the person. That is not a limitation to apologize for; it is the product.

Why bounded is better

There is a temptation to measure an assistant by how much it can do autonomously. More actions, fewer confirmations, less human involvement. That is the wrong axis for a tool that sits on top of a fleet.

The useful axis is trust. Can you leave the assistant running while you work? Can you trust its answer about what needs you without re-checking every tab? Can you let it retry a task without wondering what else it touched?

A bounded assistant is easier to trust because the failure mode is small. The worst case is a wrong recommendation or an extra task, not an unauthorized merge. That makes it reasonable to let Mira watch the queue continuously, and to treat her messages as a triage layer rather than another inbox to audit.

Attention, not autonomy, is the useful part.

Proactive, not noisy

An assistant that only answers when asked is still a chat pane. Mira comes to you.

Approvals, failures, waiting tasks, and review-ready work become proactive messages with a sidebar badge and an OS notification when no window is focused. You do not have to poll tabs to find out that a task is waiting for a permission prompt.

The hard part of proactive is not sending more messages. It is sending fewer, better ones. Workbench uses deduplication, an hourly budget, and quiet hours to keep the assistant from becoming noise.

The result is a queue that taps you on the shoulder when something needs a decision, and stays quiet when nothing does.

How to use her well

Use Mira for triage, not execution.

Good requests:

  • “What needs me?”
  • “What is blocked?”
  • “What changed since yesterday?”
  • “Which tasks are ready for review?”
  • “Draft a review note for the billing task.”

Requests that belong in a task, not in the assistant:

  • “Fix this and merge it.”
  • “Rewrite the module.”
  • “Push the branch.”

Mira cannot edit or merge. Sending execution to her is a category error. Create a task, let a session do the work, and use Mira to tell you what came back.

The division is clean: the queue executes, the reviewer decides, Mira watches and routes attention.

Honest limits

Mira's streamed Markdown reply is Claude Code only. Codex and OpenCode show run stages and the final reply. The assistant is not a uniform chat layer over every harness.

She is also not an autonomous orchestrator. A permission prompt still waits for a person. A review recommendation is non-binding. The task model is supervised by design.

Those limits are worth stating because the alternative — an assistant that implies more autonomy than it has — is how trust gets lost.

Monday checklist

  • Ask Mira what needs you before opening a row of tabs.
  • Use her to triage review-ready work, not to approve it.
  • Send execution to tasks, not to the assistant.
  • Keep review recommendations non-binding.
  • Set quiet hours so proactive messages stay useful.
  • Check the queue, not the chat, for the final state.

The assistant should make the fleet legible. It should not become another place where work disappears.
